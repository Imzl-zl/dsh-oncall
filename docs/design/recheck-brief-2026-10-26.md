# 问题清单复核 brief

给一个**没有本文上下文的新会话**用的任务书：把 [`feature-review-2026-10-26.md`](feature-review-2026-10-26.md) 的每一条问题，在**当前工作树**上重新核一遍，产出带证据的判定。

## 一、任务边界

- 只读复核：**不改代码、不跑测试、不改文档**；结论先给用户看，经他确认再落文档。
- 复核对象：审查页的 3.1–3.3（Critical）、4.1–4.17（Important）、5.1–5.6（Minor）。
- 产出必须能回答三个问题：**是不是真问题 / 触发条件有多窄 / 最小修法是什么**。
- 用户已经裁定、不要再翻的两件事：① 识图条件要能作用于第一跳（补 `chain.primaryNeeds`，见 4.17）；② 交接做实，先修 `newSession`，组合测试修完再补。这两条只核对"记录是否与代码一致"，不重新论证取向。

## 二、六条硬规矩（本次复核就是栽在这几条上）

1. **注释、设计页、旧审查记录都不算证据。** 只认代码分支。注释与实现相反时，以实现为准，并单独记一条「文档与代码相反」。
2. **「做不到」必须点名缺的东西。** 说某机制不可行，必须给出缺失的 API/字段名，并在 `node_modules/@deepseek-ai/**/lib/types/*.d.ts` 里 grep 证明不存在；服务类还要指出注册键（`super(ctx, "<key>")`）。**只证明"我们代码里没写"不算"做不到"**——先回答：这是缺实现（几十行），还是缺能力（上游不给）。
3. **每条断言都要有 file:line 和一句关键代码。** 行号当场核对，本仓行号漂移频繁；引一行就必须真读那一行。
4. **修法要落到现有控制流。** 说明改哪一行、复用哪条已有路径（例：条件跳过在 `index.ts:376-383`，index 0 也走这条），并给出成本（行数量级）与判据。修法经不起"哪一行"的回答，就是没想清楚。
5. **行为类结论必须能复述成一个具体场景**：用户选了什么模型、这一轮有没有图、实际打到哪条路由、用户屏幕上看到什么。复述不出来的结论，标"未验证"。
6. **判定只允许四类**：真缺陷 / 触发面更窄 / 不成立（记录有误）/ 设计缺口（文档承诺而代码没做）。四类不许混着写。

## 五、交付格式

1. **逐条表**：条目 \| 判定 \| 证据（file:line + 一句代码）\| 场景复述（选了什么模型、有没有图、打到哪、看到什么）\| 最小修法（行数量级）\| 与现记录一致/不一致。
2. **不一致清单**：只列差异，逐条写「现记录怎么说 → 代码是什么 → 建议改成什么」。
3. **需要用户拍板**：只列真正改变实现形态、且有取舍的；没有就写「无」。
4. **附录**：读代码时发现、但两份记录里都没有的问题（同一条目给四类判定）。
