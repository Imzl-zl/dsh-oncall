# Agent Note: 智能体协同是 DSH 右栏标签页，不是自定义浮层

Status: proposed

## Problem

模板把协同抽屉做成 `position: fixed` + 全屏遮罩的 720px 浮层。若照此实现，插件会自己拥有一套关闭/全屏/焦点/滚动规则，与 DSH 右栏的 dockkit 标签条、分屏、浮动、自动全屏和按会话布局并行存在。结果是：主对话被遮罩挡住，1024/800 视口没有空间却仍假装能停靠，焦点可以走到遮罩背后，且同一功能出现两个载体。后续再想回归原生右栏，要拆掉整套自建层。

## Decision

智能体协同只注册为 DSH 右栏标签页：类型走 `ctx.sidebarRightTabs.register`，正文走 `sidebar.right.pane.tab`，打开用 `ctx.sidebarRight.openTab`；默认全局，单会话下钻只读其他会话。不自建 `fixed` 抽屉、遮罩、标签条或会话头按钮。

准入门槛（可机械判定）：

1. 代码里没有 `position: fixed` 的协同抽屉、没有 backdrop、没有自绘关闭/全屏按钮；标签条 DOM 由 dockkit 提供。
2. 1440 / 1024 / 800 视口的右栏宽度由 DSH 列求解器给出，分别约为 648 / 568 / 344；页面不出现横向溢出。
3. 打开标签会同步展开右栏；关闭/隐藏标签后正文卸载，不留下在飞请求或动画。
4. 全局视图读 `sessions.list` + `workspaces`；单会话视图可下钻，返回后保留筛选/滚动位置；其他会话只读。

## Alternatives considered

1. 自建 `fixed` 浮层 + 遮罩（模板做法）
   - 最强的理由：不依赖 DSH 标签 API，任何按钮都能打开；宽度可自由定到 720px，视觉上最容易做成“赛博大抽屉”。
   - 为何被否：它和 DSH 的右栏、分屏、焦点、自动全屏、按会话 store 全部冲突；遮罩直接毁掉“边聊边看”的核心场景；1024/800 视口下不是变小而是遮住主列。自建层越完整，回归原生越贵。
2. 把协同做成主列页面
   - 最强的理由：960 列空间充足，复用现有 `RouterPage` 的页头/页签/保存条，不需要处理右栏宽度与容器查询。
   - 为何被否：运行视图必须常驻，用户不能为了看一眼子智能体就离开对话；主列页面也没有“当前会话”的自然上下文，切会话等于重新进入。
3. 默认用 dockkit 浮动面板（floating panel）
   - 最强的理由：可以按用户选择的大小浮在任意位置，空间比 344px 停靠大，也不挤压主列。
   - 为何被否：浮动是用户在原生右栏里主动选择的次级形态，不是默认载体；默认浮动会遮挡内容，并且仍然要自己处理焦点/拖动/层级。原生停靠 + 用户拖动/全屏已经覆盖“空间大”的需求。

## Consequences

- 收益：不阻塞主对话；自动获得分屏、全屏、拖动、焦点归还和按会话布局；不再维护一套自建抽屉；浅色/深色只跟 token 走。
- 代价：必须遵守 DSH 的宽度约束（800 视口只有 344px，<768 自动全屏）；标签标题要短；标签状态按会话，用户切到别的会话时不一定已打开这个标签，需要 `openTabIn` 或 guide entry 重新打开。
