# Agent Note: 子智能体图只画主会话到直接子节点

Status: proposed

## Problem

模板把协作画成 `主控脑 → coder-expert → security-auditor` 的纵向链，激光线从 coder 指向 reviewer。它把“复核”误读成 coder 的子会话，也把并发子智能体压成一条串行流水线。若照此实现，UI 会暗示一个 DSH 里不存在的关系：`subagentCatalog` 只列出父会话的直接子会话，复核者同样是父会话的子会话；复核是角色与 `finish{reviewId}` 账本状态，不是父子边。用户会据此误判“谁在等谁”，而实现无法用真实数据填这张图。

## Decision

拓扑只表达“本会话主智能体 → 直接子节点”。复核用角色标签、虚线卡和账本状态表达，不画成子链；只在运行中的节点/边上做动效；不引入紫色等新语义色。

准入门槛（可机械判定）：

1. 图的边只来自 `subagentCatalog` 的父子关系；没有为了“故事性”新增的 coder→reviewer 边。
2. 复核者与工作者是同级节点；`role: review` 只改变标签/卡样式/账本读取，不改变层级。
3. 超过 8 个直接子节点时显示 `+N`，不把节点缩到不可读；更深层节点在未加载时明确写“未加载”，不画虚线猜。
4. 运行中节点最多 2 个持续动画元素；`prefers-reduced-motion` 下全部关闭；完成/空闲节点不呼吸。
5. 复核不使用紫色/新色；颜色只表达状态（绿/琥珀/红/中性）。

## Alternatives considered

1. 纵向链式（模板做法）
   - 最强的理由：叙事清楚，“主脑派人 → 工人干活 → 审计签字”，一条线就能讲完；动画也最容易做。
   - 为何被否：它画的是错误关系。复核者是父会话的直接子节点，不是 coder 的子节点；并发子智能体也不是串行队列。用真实 `subagentCatalog` 填不出这条链，最后只能编数据。
2. 完整 DAG（嵌套子节点 + 复核边）
   - 最强的理由：表达力最强，能展示任意深度的委派和复核关系；视觉上也最像“图”。
   - 为何被否：DSH 默认 `maxDepth` 为 1，client 只有直接子节点目录；要画完整 DAG 就得逐层加载并在缺层时猜。复核不是结构边，硬画会制造第二真相源；自由布局在 344px 下不可读，也难做键盘/读屏。
3. 纯看板（按状态分列，不画关系）
   - 最强的理由：最容易扩展到几十个智能体；没有边和布局问题；状态扫描快。
   - 为何被否：丢掉了“都属于这个会话、从主会话派出”的空间线索，也丢掉了用户要的“子智能体动画图”；看板列会和下方智能体卡重复。
4. 力导向自由图
   - 最强的理由：节点多时自动分布，视觉上最有“赛博协同”感。
   - 为何被否：位置不稳定、每次刷新都跳；344px 下节点重叠；无法保证阅读顺序；动画成本高，且对“谁派了谁”没有额外信息。

## Consequences

- 收益：图能被真实投影填满；复核和并发的关系不再误导；窄栏也能稳定阅读；动效有明确语义；不引入新色。
- 代价：视觉上不如“激光纵链”戏剧化；超过 8 个节点要折叠；多层级只能逐层展开；用户需要读角色标签才能区分复核与工作。
