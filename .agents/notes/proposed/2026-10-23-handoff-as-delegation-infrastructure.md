# Agent Note: 交接不做任务状态判断，做委派基础设施与收工回执

Status: proposed

## Problem

"长任务跑到一半自己停了"这件事，上一版提案把它当成一个**判定问题**：从 goal / todo / 压缩次数里挑一组谓词，
配上 `when → 动作` 的规则表，由插件算出"这是遗留"再派子智能体。

问题在于 DSH 里没有"任务处于什么状态"这个真值。谓词表一旦落地，插件就必须先定义"完成"长什么样，而这本来
是模型的判断。词表不全时用户只有两条路：加谓词（枚举的连续体），或者绕开配置直接改代码。两条路都让插件从
"执行用户意图"变成"猜用户意图"，而且新增场景的代价落在插件而不是配置上。

## Decision

交接 = **委派基础设施**（名册 + 工具 + 备料 + 原生唤醒），不是判定器。插件不判断任务状态，只守三件机器能做的事：
菜单由用户配、选择由模型做、协议是否被遵守由插件记账。

准入门槛（可机械判定）：

1. **插件代码里不出现任务状态谓词**：没有 `if (goal.active)` / `if (todos.pending > 0)` 之类的分支来决定
   派不派人；`turn-stopping` 里唯一的读取是"本回合有没有调用过 `handoff`"，用于协议记账。
2. **名册是唯一的候选人来源**：模型不能传 `provider/model`/`preset`，只能传 `roster[].id`；名册外的 id 直接报错。
3. **收工回执是唯一的"这一轮结束了"声明**：`handoff{action:'finish'}` 三个取值 `done|human|abandon`；
   有 active goal 时 `done` 被拒，完成仍以 goal 为唯一权威。
4. **备料只来自会话事实**：`attach` 的每一项都能在 `docs/design/handoff-proposal.md` §4.3 的封闭词表里找到来源；
   任何"模型的总结"不进载荷。
5. **子会话与顶层会话共用同一套路由**：第一跳 = 该请求自己声明的模型（顶层是用户选中，子会话是名册钉死或继承）；
   失败后的候选来自"会话自己的绑定 → `parentSession` 的绑定 → 默认链"，名册的 `failover` 可覆盖为 `none` 或指定链。
   不存在"子会话跳过路由"的分支；重试与熔断对子会话同样生效。
6. **循环由预算收敛**：自主预算按"自最近一条用户消息"计，分派发 / 复核 / 重启三本账；到达上限后只能
   `finish{human}`。三本账都是**上限不是配额**：通过即收工，不强制跑满。复核 verdict 为"有缺口"时 `finish{done}`
   被拒，想 done 必须再复核一次——每轮再复核消耗一次预算，所以"审 → 改 → 审 → 改"必然终止，不靠模型自觉。

## Alternatives considered

1. **`when` 谓词 → 动作的规则表**（上一版提案）
   - 最强的理由：零模型成本、结果可预测、能在设置页里画成一张表，也不依赖模型是否听话。
   - 为何被否：它把"任务处于什么状态"变成插件必须先定义的量，而状态是模型的判断。场景一多就必须扩词表，
     扩词表就是枚举；用户明确拒绝这个形态，且每次扩词都要求插件先猜一遍。
2. **由插件在 `turn-stopping` 自动派复核（不问模型）**
   - 最强的理由：人不在也断不了，触发完全确定，不依赖模型调用工具。
   - 为何被否：派谁、派去干什么只能靠猜，复核者拿不到意图只能盲审；每轮都派则费用不可控。它解决的是
     "别断"，代价是"派得不对"，而派得不对的复核比不派更贵。
3. **只靠原生 `subagent` 工具 + 模型自选模型/人格**
   - 最强的理由：零新增配置，DSH 已经支持 `agentPreset`、`allowedAgentPresets` 与模型白名单。
   - 为何被否：用户要的是**指定**渠道/人格/工具；让模型每轮现场拼 `agentOptions` 等于每次重配，也无法预先
     定义"复核者只读不改、且不读主模型自述"。名册是预置菜单，不是限制。
4. **插件自建任务状态机（open / handed-off / done）**
   - 最强的理由：能画进度、能做准入门、能跨会话统计。
   - 为何被否：第二个真相源。goal 与 todo 已经是模型写下的声明，再加一个只会让"到底谁说了算"变成新的调试面。
     回执只记"谁在什么时候说了什么"，不记任务状态。
5. **`delivery:'caller'` + 插件自己 `followup`**
   - 最强的理由：结算消息的内容与时机完全可控，能精确拼装"结论 + 指令"。
   - 为何被否：`caller` 明确不通知父会话（`packages/subagent/subagent/src/manager.ts:1188`），要自己实现空闲
     判断、队列、去重，等于重写 `notifySettlement`；原生那条路径已经处理了 idle/running 两种父状态。
6. **子会话完全绕开路由链**
   - 最强的理由：钉死的就是钉死的，绝不会因为降级偷偷换成更贵的模型；行为最容易解释，也最省钱。
   - 为何被否：它让子智能体成为系统里唯一没有韧性的执行者。熔断状态本来就全局，子会话踩坏的渠道主会话照样会踩，
     绕开并不能隔离，只是让一次可恢复的渠道抖动升级成一次任务失败。想钉死用 `failover: none`，想省钱用一条
     便宜的专用链——都不需要一个全局例外。

## Consequences

- 收益：新增场景靠"再建一个角色 / 改一句 brief / 调一个闸门"表达，不需要插件加谓词；插件的判断面收缩到
  "协议记账"，复核质量随模型与 preset 提升而提升。路由与交接可以各自单独开，也可以叠加：叠加时子会话与顶层
  会话共用同一套重试/熔断/切换，子会话踩坏的渠道对主会话同样算数。"审 → 改 → 审"由预算收敛，不需要插件判断
  任务有没有做完。
- 代价：**模型不调用就什么都不会发生**。没有 goal 也没有 todo 的会话，`turn-stopping` 那一层没有可依据的
  声明，只能靠模型自觉（写进 `handoff-proposal.md` §9）。另外每个名册项都要用户手工写好 `purpose`——写得含糊，
  模型就会选错人，而这个错误插件无法在运行时识别。子会话失败后可能被降级到另一条渠道，花费不再只由名册的
  `provider`/`model` 决定；要钉死必须显式写 `failover: none`。
