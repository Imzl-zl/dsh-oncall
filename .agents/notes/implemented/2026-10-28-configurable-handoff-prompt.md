# Agent Note: 新会话提示词 = 可改的模板 + 配置的常驻要求 + 模型写的交接说明

Status: implemented

## Problem

用户手动换会话时有两类习惯：长清单做了一半，让 AI 写"新会话提示词：继续实施 X，要求 Y"；或做完一两个小问题，让 AI 写"审查当前已变更，要求 Y"，借新会话避开被压缩的上下文。这两段提示词现在由模型在 `handoffNote` 里现写——内容好不好全靠它当场的判断，用户想把"要求 Y"固定下来（每次都带）时没有位置可放，只能每次在对话里重复说一遍。

同时，新会话收到的第一条消息是插件硬编码的几行中文，改不了措辞；想加一句自己的话只能靠模型写进 note。

## Decision

把"新会话收到的第一条消息"拆成三层，各归各的拥有者：

1. **模板**（`newSession.promptTemplate`，默认 = 发布时的措辞）：界面里可改字、删段、换顺序；占位符只有 `{reason}` `{nextAction}` `{extra}` `{note}` `{report}` `{artifacts}`。
2. **常驻要求**（`newSession.promptExtra`，默认空）：配置一次，每次接力都带进 `{extra}`；空则整行不出现。这是"要求 Y"的确定性落点。
3. **交接说明**（`{note}`）：仍然只能由模型写——它是那次工具调用的参数，插件不生成、只校验非空。

渲染规则只有一条：**一行里的占位符被替换成空，整行删掉**。这让默认模板的渲染与"模板化之前"逐字一致（`{report}` 空 → 没有空标题；`{artifacts}` 空 → 没有空分区）。

保存期拒绝两种模板：缺 `{note}`（新会话拿不到任务）、出现不认识的占位符（写错的 `{xxx}` 会原样印进提示里，没有任何提示）。

## Alternatives considered

1. 只做"附加要求"，模板保持硬编码
   - 最强的理由：改动最小、没有模板语法要维护，用户最常想固定下来的就是"要求 Y"。
   - 为何被否：用户明确说"默认一个提示词，用户可以自己配置发啥"——他要的是能改那段话本身，不只是追加一句。只加 extra 会把"改措辞"继续留给模型。
2. 整个简报不由模板渲染，改成"用户写一段前缀，插件在后面无条件附上工件与 note"
   - 最强的理由：用户不可能写坏结构，`{note}` 与工件永远在。
   - 为何被否：那就等于"只能换开头几行"，用户想调顺序（比如把工件挪到最前）做不到；而"必须含 `{note}`"这条规则同样能防住"把任务弄丢"，成本更低。
3. 让模板支持条件段（`{nextAction=review}` 之类）
   - 最强的理由：一段模板同时覆盖"继续实施"和"审查"两种转场。
   - 为何被否：模板语法一旦有条件就会长成第二套配置语言，而这种情况用两个配置档（`nextAction` + `extra`）已经能表达；真需要两套措辞的用户可以把要求写进 roster 的 instructions 或对话里。

补记（同日，用户追问“上一个会话怎么知道要交接”）：模板与 `{extra}` 只解决“通用部分”，
**模型并不知道何时该交接、note 里该写什么**——工具描述原来只说了有 `newSession` 这个动作，以及配了
`onFinish` 时 `finish` 必须带 note。已在 `compileDescription` 补两句：何时交接（用户点名要新会话/新会话提示词、
本回合完成而下一步是复核或独立任务、上下文被反复压缩而任务还长），以及 note 的五要素（已完成的边界、
下一步与涉及文件、不要重做、先读什么、用户给的验收要求），并写明“只写继续不算交接”。
判据是 `unit`：描述里必须出现这两句与五要素，且仍然**不出现**角色的 `instructions`（那是子会话的读者）。

## Consequences

- 收益：用户把"要求 Y"写一次就永久跟着走（不再靠模型记），模板措辞也能改；默认渲染与旧行为逐字一致（现有 `【接力】`/`【交接说明】` 断言同时成了回归网）。
- 代价：`handoff` 段多两个文本字段与一套占位符语法（schema 长度上限、浏览器归一化、结构规则、界面各一处，两份字典各 6 个键）；模板写坏会挡住保存，用户需要读懂占位符含义——所以界面上把可用占位符与"空占位符删整行"的规则写在字段提示里。`{note}` 仍由模型写，模板再漂亮也治不好"模型写得敷衍"这一类质量问题。
