# Agent Note: 入口令牌走环境变量，且在无持久存储时拒绝启动

Status: implemented

## Problem

入口一旦打开就会持有两样危险的东西：一个能代表 agent 身份的 GitHub 令牌，和一份"哪条外部消息已经变成过 Case"的记忆。两者都容易用最省事的方式接错：

- 令牌写进配置最方便——配置就在设置面板里，填一个字段就完事。但那份配置会落进 profile 的 `cordis.patch.yml`，进入备份、被复制到别的机器、也会出现在任何打印配置的日志里。
- 没有 `storageDomain` 的装配里退化成内存存储最省事——这样任何组合都能跑。但入口的记忆是**幂等键的载体**：内存账本一重启就空，于是每一条还留在回看窗口里的历史消息都会重新开一个 Case。

## Decision

令牌只从环境变量 `GITHUB_TOKEN` 读；入口在没有持久存储的装配里不启动，打一条错误日志并保持关闭。

准入门槛（可机械判定）：

1. 配置 schema 里没有令牌字段。想加必须先改这条笔记。
2. `DurableLedger.persistent` 为假时，`installIngress` 必须 `logger.error` 并不启动循环（`src/index.ts` 的 `installIngress`）。
3. 令牌读取只允许经过 `src/faces/env.ts` 的 `envOf`：一处读，一处能审。

## Alternatives considered

1. 令牌作为配置字段，界面里填
   - 最强的理由：五分钟接上是产品力的第一条（`docs/design/super-plugin.md` 十一节），环境变量是让用户去开终端、改 shell profile、再重启进程——比填表单重得多。
   - 为何被否：配置是**会被复制和粘贴的东西**。一个长期令牌进了 `cordis.patch.yml`，就等于进了每一次备份、每一位协作者的本地副本，以及每一份贴进 issue 的配置。接上的成本转移到"删掉一个泄露的令牌"上，而后者贵得多。折中是保留表单但只写环境变量名——那又变成两个事实（名字在哪配、值在哪读），所以只留环境变量这一条路。
2. 没有 `storageDomain` 时退化成内存账本，保持入口可用
   - 最强的理由：与 `bindings.ts` 的既有行为一致——它对无存储的装配回退到内存，并如实告知浏览器。一致性本身就是维护成本的理由。
   - 为何被否：两者的失败代价不同。绑定丢失只是"这条会话回到默认链"，用户看见 chip 变了就能改回去；入口的幂等键丢失意味着**同一句 @ 会再开一个 Case**，而两个 Case 会去改同一批文件。所以路由可以退化，入口不能。
3. 把令牌读进 `Config` 的默认值（`z.string().default(envOf(...))`）
   - 最强的理由：一处定义，界面里能看到"已从环境变量读到"，用户不必猜。
   - 为何被否：schemastery 的默认值会随配置一起**保存**，也就是第一次保存就把环境变量的值固化进了配置文件——正好是方案 1 的问题，而且更隐蔽。

## Consequences

- 收益：配置里没有任何秘密；入口在任何没有持久存储的组合里都不会半速运行，也不会制造重复 Case。守卫与测试都能证明这两点（`tests/ingress-loop.mjs` 的"没有 storageDomain 的装配"与"域没打开时 commit 报错"）。
- 代价：上线多一步（设环境变量并重启），与"五分钟接上"有摩擦。另外 `persistent` 是同步属性、`ready` 是异步的，调用方必须**先 await 再读**——写反了就会在域打开前判定为"无持久存储"，把可用的装配误判成不可用。这一条由 `installIngress` 的 `.then` 顺序保证，没有类型能防。
