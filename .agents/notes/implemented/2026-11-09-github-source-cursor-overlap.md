# Agent Note: 游标回看一分钟，重复靠键吸收

Status: implemented

## Problem

GitHub 的 `since` 过滤是「更新大于等于此刻」。用它做游标有一个必然的竞态：查询发出到游标落库之间创建的事件，下一次查询的 `since` 已经越过了它，于是**永远读不到**。这个错误没有任何声音——没有异常、没有空结果的区别，只是某条 issue 从此没人管。

第二个来源是时钟：我们的 `now` 与 GitHub 的 `updated_at` 不是同一个时钟，几秒的偏差就足以让边界上的事件落在两次查询之间。

## Decision

每次 poll 把游标推进到 `now - 60s`，下一次会重复读到窗口内的事件；重复由 `TriggerKey` 吸收，不由游标保证。游标读不出来时当作没有游标（退回回看窗口），绝不当作「已读到最新」。

准入门槛（可机械判定）：

1. 同一事件在两次 poll 中被上报，两次的 `TriggerKey` 必须逐字相同（`tests/github-issue.mjs` 的「窗口内的重复上报」一例）。
2. 任何情况下不允许「游标解析失败 → 跳过」。解析失败必须退化成首次 poll 的回看窗口。
3. `poll` 不得自己写游标；游标由调用方在同一事务里与 Case 一起落库。

## Alternatives considered

1. 游标取 `max(updatedAt)`，精确不重复
   - 最强的理由：零重复，最省一次扫描；游标语义也最直观——「我读到这里了」。
   - 为何被否：`updatedAt` 会**倒退**。一个 issue 被关闭、被改标签、被重新打开，最大值可能不是最新的那个；一旦取到倒退的值，`since` 回退会引发大范围重复，而取到偏大的值就永久丢事件。一个会反向移动的量不能当游标。
2. 用 GitHub Notifications API 当游标
   - 最强的理由：服务端排序、有稳定的 `id` 与 `last_read_at`，天然解决顺序与去重，不必自己算窗口。
   - 为何被否：通知是**按人**而不是按仓库的，需要 notification 权限；而且标记已读是破坏性动作——用它做游标意味着 agent 会把用户自己的通知标成已读。为一个读位点去动用户的收件箱，代价远超收益。
3. 每个 thread 存「最后见过的评论 id」
   - 最强的理由：最精确，重复为零，且能表达「这条评论我处理过了」。
   - 为何被否：需要为每个 thread 维护一行并随仓库规模线性增长；更关键的是它**不能让 API 少返回**——`since` 仍然要传，于是既要精确记账，又省不下请求，两头付钱。

## Consequences

- 收益：漏事件的两种来源（查询竞态、时钟偏差）都被一个窗口覆盖；游标退化成纯粹的省流量手段，它坏掉最多多读一轮，不会丢工作。实现只有一条表达式，测试可以逐字断言窗口边界（`GITHUB_OVERLAP_MS`）。
- 代价：每次 poll 会重复上报窗口内的事件，因此**存储层必须按 `TriggerKey` 去重**——这不是可选项，是这套设计的前提。另外窗口是固定 60 秒，对极端慢的仓库（单次 poll 超过一分钟）不足；届时需要把窗口参数化，而不是靠加大常量。
