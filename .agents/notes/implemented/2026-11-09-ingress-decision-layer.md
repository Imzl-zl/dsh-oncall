# Agent Note: 入口决策层用「状态派生 + 三值闸门」，并把守卫收窄到两个新目录

Status: implemented

## Problem

入口这一层要落的第一批代码是「一条外部事件该不该变成一件工作」。它有三个容易写坏的地方，而且坏掉时都不报错：

1. **状态存不存**。若把 Case 的状态写进表，它就与 `case` / `step` 记录构成两份事实；任何一次「写成功、状态没更新」都会让面板显示的东西和真实进度不一致，且没有哪一边是权威。
2. **拒绝算不算异常**。若拒绝抛异常，调用方就得用 `try/catch` 做流程控制，而「这个人不在白名单」是每条陌生消息都会走的正常路径，不是意外。
3. **守卫的范围**。现有树里 `src/config.ts` ↔ `src/rules.ts` 已有一处值依赖成环（`config.ts:56` 值依赖 `rules.ts`，`rules.ts:20` 反向类型依赖）。若守卫一上来就要求全树无环，它第一天就是红的，而红的守卫活不过一周。

## Decision

入口第一刀只落两个新目录 `src/contract/` 与 `src/core/`：状态一律派生不落库；拒绝用结果值、失败用异常；守卫只守这两个目录，全树已知债务只报告不失败。

准入门槛（可机械判定）：

1. `src/core/*` 只 import `src/contract/*` 与 `src/core/*`；`src/contract/*` 只 import 自己。越界即 `tests/layers.mjs` 失败。
2. 两个目录里不得出现 `ctx.`、`Date.now(`、`Math.random(`、`.append(`、`.put(`、`await `。出现即失败——时间与随机数只能作为参数进来。
3. `src/core` 与 `src/contract` 内无环。全树若有环，只在输出里点名，不判失败。

## Alternatives considered

1. 守卫一开始覆盖全树
   - 最强的理由：一处规则一处执行，没有「新代码守、老代码放」的双标；也强迫立刻还清 `config ↔ rules` 的债。
   - 为何被否：还债需要先搬 `assertStructural` 并改调用点，那是独立的一次行为无关迁移。把守卫和迁移绑在一起，第一天必然红；而一个长期红的检查会被注释掉或加白名单，最后比没有更糟。代价是这份债务以「输出里点名」的方式显式存在，而不是被隐藏。
2. 状态落库，每次写记录时同步更新
   - 最强的理由：读面板时不用重算，且可以直接按状态建索引、做筛选。
   - 为何被否：两份事实必然漂移，且漂移方向不确定（记录新、状态旧，或反之）。派生只花一次纯函数调用，而漂移的排查成本是「这个 Case 为什么卡在 working」这类无法复现的问题。
3. 拒绝写成异常（沿用现有 `gateRefusal` 的形状）
   - 最强的理由：与现有代码一致，工具边界本来就把拒绝转成异常给模型看。
   - 为何被否：「不在白名单」是陌生消息的默认结果，不是异常。真正需要一致的是**边界只转换一次**：纯函数返回结果值，面向模型的工具边界把结果值转成异常。这与现有形状并不冲突，只是把转换点从核心里移出去。

## Consequences

- 收益：`src/core` 里的四个模块零依赖、零 mock，25 条表驱动用例在毫秒级跑完；守卫实测能抓到违规（临时插入 `Date.now()` 立即报红）；现有五套件数字未变（unit 259 / client-controller 129 / remote 25，外加 handoff-relay 与 37 个组合场景全过）。
- 代价：入口类型里必须显式保留 `ambient`（人说了话但没点名），否则闸门无法在不猜测意图的前提下拒绝它——这是写测试时才暴露的缺口，说明「类型驱动」并不能免除先想清楚语义。守卫目前只覆盖 7 个文件，全树仍有一处成环的债务待还（`docs/design/super-plugin-architecture.md` M1）。
