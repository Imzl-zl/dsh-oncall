# Agent Note: 委派路由分三档，全局默认与角色钉死并存

Status: implemented

## Problem

名册的每个角色都能写 `provider`/`model`，不写就跟随父会话。真实用法里出现了第三种诉求：**"我就是全局一个子代理模型，不想一个角色一个角色地配"**——逐角色配在角色多时是纯粹的重复劳动，而且改一次模型要改 N 处。同时另一种诉求也必须继续成立："我只建角色，模型完全跟随父会话，什么都别让我配。"

也就是说这不是"要不要多一个字段"，而是**同一条路由有三级来源**，缺任何一级都会逼用户走不合适的形态：只有角色级 → 全局用户被迫重复配置；只有全局 → 需要个别角色换模型的用户无处表达。

## Decision

在 `handoff` 段加一份全局默认 `delegateDefaults { provider, model, reasoningEffort, maxTokens }`，派发时按 **角色 → 全局 → 父会话** 取值。三者都可留空；**半条路由不是路由**，只填一半在保存期被结构规则拒（与角色里的同一条规则）。

路由**按整条取**，不做逐字段合并：不会出现"渠道来自角色、模型来自全局"这种拼出来的路由。理由不是省事，而是这种状态用户根本到不了（半条路由被拒），代码去模拟一个不可达状态只会制造两套真相。

## Alternatives considered

1. 直接读 DSH 原生那份全局子代理模型（`tool-subagent` 行的 `agentOptions`）
   - 最强的理由：用户已经能在 DSH 那边配"一份全局子代理模型"，插件跟着它走就没有第二处配置。
   - 为何被否：那是**另一个插件的配置键**，不是服务接口；键名或语义一变，我们就静默失效（我们的子代理悄悄回到继承父会话）。而且它只作用于原生 `subagent` 工具，读它等于把"原生工具的实现细节"当成我们的契约。要么读公开服务（`subagentModelSelection.current()`，那是"允许模型自选"的授权清单，不是默认值），要么自己拥有一份。
2. 逐字段合并：角色只写 `provider`、模型从全局补
   - 最强的理由：表面上更"灵活"，用户少填一个字段。
   - 为何被否：`provider` 与 `model` 是一条路由的两半，从两个来源拼出来的组合可能根本不是用户想要的渠道；而且与"半条路由不是路由"的既有规则直接冲突。
3. 只加全局、删掉角色级路由
   - 最强的理由：一个配置点，界面更简单。
   - 为何被否：需要"复核用便宜的、干活用强的"这类按角色分工的用户就无处表达；角色级是现有能力，删它是产品面收缩。

## Consequences

- 收益：三种用法都成立（逐角色 / 全局一份 / 完全跟随），且没有第二处"授权清单"；`handoff` 段的字段仍是唯一来源，界面与 host schema 同源。
- 代价：`handoff` 段多一组四个字段（schema、类型、浏览器归一化、结构校验、界面各一处）；"角色写了路由"与"用了全局默认"在回执里看不出区别——模型和用户都无法从回执反推这次用的是哪一档，只能读配置。真实使用中这一档差异不影响判断（都是用户配的），所以没有为它加一个额外的回执字段。
- 真渠道复核（同日晚）：`tests/real-handoff.mjs` 加 `DSH_E2E_DEFAULTS=provider/model` 后跑两遍，各 0 失败——不带默认时留空角色落到父会话 `real-a/glm-5.2`；带默认 `real-a/deepseek-flash` 时钉死角色仍是 `step-5-preview`、留空角色改用 `deepseek-flash`、接力会话仍是父会话那条。三条互不相同，验的是顺序。
